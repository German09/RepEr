# Пайплайн RepEr: исправления (EF) из коммитов, релиз, обновление базы

Коммит с пометкой `EF` в комментарии превращается в расширение-исправление `EF_<задача>_<n>`, где `n` -
порядковый номер EF-коммита задачи после релиза: измененные этим коммитом процедуры и функции переопределяются
через `&Вместо`, новые добавляются как есть. Исправления ставятся в базу в порядке коммитов.
Расширение собирается в `.cfe`, упаковывается в архив формата исправлений БСП и публикуется в ленту,
из которой его забирает информационная база.

## Состав

| Шаг | Чем |
|---|---|
| Исходники расширения из коммитов | `ef_build.py`, `efgen/` |
| Сборка `.cfe` и архива | `build_cfe.ps1` (ibcmd через автономный сервер) |
| Пайплайн | `../template/`, `ci_build.ps1`, `sync_repo.ps1` |
| Проверка относительно релиза | `ef_check.py` (EDT, `1cedtcli validate`) |
| Публикация в ленту | `ef_publish.py` (пакеты GitLab или каталог) |
| Проверка установки в базу | `ef_verify.py`, HTTP-сервис `reperext` расширения RepEr |
| `.cf` релиза по тегу | `release_cf.py`, задание Релиз |
| Загрузка `.cf` в рабочую базу | `load_cf.ps1`, `merge-all.xml`, задание Загрузка |
| Перезапуск кластера | `cluster_restart.ps1`, `.reper/cluster.json`, задание Перезапуск |
| Обновление и снятие блокировки | `update_db.ps1`, `cluster_restart.ps1 -Unlock`, задания Обновление и Снятие блокировки |
| Получение исправлений базой | расширение RepEr, см. [../extension/README.md](../extension/README.md) |

## Как устроена генерация

1. **Релиз-основание.** Исправление ставится на то, что работает в продуктиве, поэтому сравнение идет
   не с родителем коммита, а с релизом. Продуктив равен последнему тегу, поэтому по умолчанию берется
   ближайший тег (`git describe`); `--base` нужен только для пересборки под другой релиз.
2. **Исправление на коммит.** EF-коммит - коммит после релиза, где есть и номер задачи, и пометка `EF`.
   Каждый EF-коммит - отдельное исправление `EF_<задача>_<n>` (`EF_9634_1`, `EF_9634_2`), в нем только то,
   что изменил этот коммит. Префикс имен перехватчиков - `P_<задача>_<n>_`: перехватчики разных исправлений
   одного метода не совпадают по имени. У срочного исправления (пометка `FIRE` в теме хотя бы одного его коммита)
   в имени `FIRE_`: `EF_FIRE_9634_1`, у отката (в исправлении есть действующий `git revert` EF-коммита) - `REV_`:
   `EF_REV_9634_2` (шаблон `EF_{fire}{rev}{task}_{n}`). По `fire` в имени конфигурация находит
   срочное расширение и просит перезапустить сеансы, где оно еще старой версии. Если пометка появилась у исправления
   позже, сборка под прежним именем отзывается и публикуется под новым.
3. **Порядок установки** (`order`) - номер коммита в истории после релиза (`git log --no-merges base..head`,
   считаются все коммиты, и без пометки). Если несколько исправлений перехватывают один метод, работает
   перехватчик расширения, установленного последним, поэтому база ставит исправления по возрастанию порядка
   (см. "Получение исправлений базой"). Текст метода в более позднем исправлении уже содержит правки более
   ранних - он берется из его коммита.
4. **Объединение.** Перехватить метод, которого нет в релизе, нельзя (`&Вместо` - только для методов
   конфигурации), а добавить его в два расширения - получить два одноименных метода в одном модуле. Поэтому
   коммиты, которые меняют или вызывают один и тот же метод или общий модуль не из релиза, собираются
   в одно исправление: имя - по первому коммиту, порядок - по последнему, текст - из последнего. Причины
   объединения - в `report.md`, раздел "Собраны в одно исправление".
5. **Версия сборки** - `<версия библиотеки>.<число коммитов исправления>` (`1.3.19.01.1`). Префикс версии - версия библиотеки, она же каталог
   ленты, а не тег: теги неоднозначны (`3.17` и `3.17.2` - библиотеки `1.3.17.01` и `1.3.17.02`), и номера
   исправлений разных выпусков библиотеки не пересекаются. Если в ленте релиза (`--feed-url`, `--feed-dir`) уже есть
   сборка исправления с другим набором коммитов и тем же или большим номером, номер - наибольший
   опубликованный + 1: у сборок с разным содержимым версия и UUID не совпадают, и база ставит новую сборку.
   Сборка с тем же набором коммитов получает прежнюю версию.
6. **Затронутые методы.** Для каждого коммита сравниваются версии модуля до и после. Сравнение идет
   по методам, комментарии и отступы не учитываются.
7. **Итог относительно релиза.** Текст метода берется из коммита исправления (у объединенного - из последнего):
   - метод есть в релизе и отличается от него - `&Вместо("Имя")`, перехватчик получает имя `P_<задача>_<n>_Имя`,
     `Экспорт` снимается. Метод, вернувшийся к тексту релиза, тоже перехватывается, если его перехватывает
     исправление с меньшим порядком: иначе в базе работал бы прежний перехватчик;
   - метода в релизе нет - добавляется как есть, вместе с документирующим комментарием;
   - общего модуля в релизе нет - модуль добавляется в расширение целиком как собственный объект.
   Директивы компиляции (`&НаСервере` и т.п.) и условия `#Если`, в которые вложен метод, сохраняются.
8. **Откаты.** Коммит, который откатил `git revert` (в теле "This reverts commit ..."), исправлением
   не считается, его исправление отзывается; откат отката возвращает коммит. Сам откат - обычное
   исправление с `REV_` в имени (`revert` в `ef.json` и оглавлении ленты), название - как у откаченного коммита
   (тема `Revert "..."` разворачивается): он возвращает методы к прежнему тексту поверх более поздних исправлений; если после
   отката метод совпал с релизом и его никто не перехватывает, исправление пустое и не собирается. Откат
   изменения, которое уже в релизе, в исправление не переносится. Отзыв: в каталоге только `ef.json`
   с `"revoke": true` и `report.md`, сборка и проверка его пропускают, а публикация помечает все сборки
   исправления в ленте `revoked`, и базы их удаляют.
9. **Манифест.** В расширение кладется общий макет с именем расширения - описание исправления в формате
   XDTO-пакета `Patch` из БСП. По нему БСП показывает описание в списке установленных исправлений,
   различает исправления по UUID и удаляет устаревшие при смене версии. Применимость:
   библиотека `applied_name` из `config.json`, версия из модуля `version_module` на момент релиза.

Результат в `build/ef/EF_<задача>_<n>/`: `xml/` (выгрузка конфигуратора), `<проект>.EF_<задача>_<n>/` (проект EDT),
`Manifest.xml`, `report.md`, `ef.json`, после сборки - `EF_<задача>_<n>.cfe` и `EF_<задача>_<n>.zip`.
В `ef.json` и оглавлении ленты, кроме прочего, `order` - порядок установки и `methods` - что исправление
перехватывает и добавляет (`CommonModule.Модуль.Метод`).

**Что собирается.** `--commit X` (как `--range X^..X`) и `--range A..B` сравнивают исправления по истории
до `A` и до `B`: собираются новые и изменившиеся (другой набор коммитов), отзываются исчезнувшие (коммиты
откачены или вошли в другое исправление). С лентой (`--feed-url`, `--feed-dir`) отзываются и действующие
исправления ленты, которых по истории нет, если все их коммиты есть в истории до `B` - так уходят исправления
прежней схемы `EF_<задача>` (одно на задачу), а запуск по старому коммиту не отзывает более новые.
`--task` собирает все исправления задачи, `--commits` - одно исправление из явного списка коммитов
(номер в имени - короткий хэш последнего коммита).

## Что генератор не переносит

Все такие изменения перечисляются в `report.md` в разделе "Не вошло в исправление":

- модули форм - заимствование формы тянет за собой копию формы и зависимые объекты;
- метаданные, формы, права, макеты, индексы;
- код вне процедур и функций: переменные модуля, тело модуля;
- модули видов объектов, которых нет в `efgen/kinds.py`. Сейчас есть: общие модули, справочники,
  документы, обработки, отчеты, регистры сведений и накопления.

В разделе "Проверить" отчета - то, что перенесено, но требует взгляда:

- метод после релиза меняли и другие коммиты: их правки тоже попадут в исправление;
- метод вызывает то, чего нет в релизе и нет в исправлении (`--pull-deps` добавит такие методы сам);
- метод удален: расширением это не выразить.

## Структура

| Путь | Что это |
|---|---|
| `ef_build.py`, `efgen/` | генератор исходников расширения из коммитов |
| `build_cfe.ps1` | сборка `.cfe` и архива исправления через ibcmd |
| `ef_check.py` | проверка в EDT относительно релиза |
| `ef_publish.py` | публикация в ленту исправлений |
| `feed_copy.py` | копия ленты (пакета generic) в другой проект GitLab при переезде пайплайна |
| `release_cf.py` | `.cf` релиза по тегу: выгрузка проекта из EDT в XML и сборка ibcmd |
| `load_cf.ps1`, `merge-all.xml` | загрузка `.cf` релиза в основную конфигурацию рабочей базы объединением, без обновления базы данных |
| `cluster_restart.ps1`, `.reper/cluster.json`, `.reper/known_hosts` | перезапуск кластера рабочей базы с блокировкой и очисткой `snccntx*`, снятие блокировки (`-Unlock`) |
| `update_db.ps1` | обновление конфигурации базы данных и версии (Предприятие) под блокировкой, ожидание фоновых заданий |
| `rac.ps1` | общие функции `cluster_restart.ps1` и `update_db.ps1`: внешние программы, RAS (`rac`) |
| `ef_verify.py` | ожидание установки опубликованных исправлений в базу (HTTP-сервис `reperext` расширения RepEr) |
| `ci_build.ps1` | шаг CI: генерация и сборка по коммитам push |
| `sync_repo.ps1` | зеркало репозитория конфигурации на раннере |
| `setup_server.ps1` | разовая настройка сервера раннера: рабочие каталоги и автономный сервер сборки службой |
| `../template/` | `.gitlab-ci.yml` проекта и `.reper/reper.gitlab-ci.yml`: пайплайн исправлений, задания Релиз, Загрузка, Перезапуск, Обновление, Снятие блокировки |
| `.reper/config.json` | настройки проекта: корень исходников, шаблоны номера задачи, имени расширения и префикса, режим совместимости, имя и источник версии для манифеста |
| `tests/` | тесты разбора и генератора на временном репозитории |

Репозиторий конфигурации инструмент не меняет: читает историю git и пишет результат в `--out`.
Настройки проекта передаются через `--config` или переменную окружения `EF_CONFIG`.

## Запуск

Примеры - из каталога репозитория, результат в `build/ef`:

```bash
# исправление по EF-коммиту (задача берется из комментария)
python ef_build.py --repo D:/git/system --config .reper/config.json --commit HEAD

# все исправления задачи после релиза
python ef_build.py --repo D:/git/system --config .reper/config.json --task 9634

# исправления, изменившиеся в диапазоне, и отзыв исчезнувших - так запускает CI
python ef_build.py --repo D:/git/system --config .reper/config.json --range 3.19..HEAD

# явный список коммитов, если пометки EF в комментариях нет
python ef_build.py --repo D:/git/system --config .reper/config.json --commit 39d5c101fa --task 9337 --commits 55528db330,39d5c101fa

# сборка .cfe и архива через автономный сервер
powershell -File build_cfe.ps1 -EfDir build/ef/EF_9731_1 -Platform "C:\Program Files\1cv8\8.3.27.2325\bin" -ServerData D:\cicd\ibsrv

# проверка в EDT относительно релиза
python ef_check.py --repo D:/git/system --config .reper/config.json --workspace D:\cicd\ws-release --edt-cli D:\EDT\components\1c-edt-<версия>\1cedtcli.exe

# .cf релиза по тегу в D:\CF\3.19
python release_cf.py --repo D:/git/system --config .reper/config.json --tag 3.19 --workspace D:\cicd\ws-release --edt-cli D:\EDT\components\1c-edt-<версия>\1cedtcli.exe --platform "C:\Program Files\1cv8\8.3.27.2074\bin" --dest D:\CF

# публикация в ленту
python ef_publish.py --ef-dir build/ef/EF_9731_1 --feed-dir \\server\share\ef

# тесты
python -m unittest discover -s tests
```

Коды возврата `ef_build.py`: 0 - сформировано, 2 - формировать нечего, 3 - с `--strict` часть изменений
не перенесена.

## Подключение к CI

Пайплайн ставится в репозиторий конфигурации скриптом `install.ps1` из корня RepEr
(`powershell -File install.ps1 -Target <репозиторий>`):

- `.reper/pipeline/` - эти скрипты без тестов, `.reper/reper.gitlab-ci.yml` - задания, `.reper/VERSION` - версия RepEr.
  Заменяются при каждой установке, руками в проекте не правятся;
- `.gitlab-ci.yml` (include заданий и значения переменных проекта), `.reper/config.json`, `.reper/cluster.json` -
  создаются, только если их нет: заполнить под проект. Ключи узлов кластера - в `.reper/known_hosts`.

Задания Сборка, Проверка, Публикация, Установка идут на push в основную ветку, диапазон
`CI_COMMIT_BEFORE_SHA..CI_COMMIT_SHA`. Публикация идет сразу после успешной проверки, без кнопки. Установка ждет,
пока база поставит опубликованные исправления, см. "Проверка установки". Ручной запуск (Run pipeline) - с переменными
`EF_BEFORE_SHA` и `EF_HEAD_SHA`. Тег запускает задания Релиз и Загрузка, см. "Сборка .cf релиза". Ветки, кроме
основной, и merge request пайплайн не запускают.

Задания выполняются на раннере с доступом к рабочей базе и кластеру, а что на нем запускается, определяют файлы
репозитория конфигурации: кто может пушить в основную ветку, тот может выполнить на раннере что угодно. Поэтому
основную ветку защитить (изменения - через merge request), раннер сделать protected и не ставить его
на центральный узел кластера, если пушить в основную ветку могут многие.

Защита рабочей базы:

- релиз запускают только защищенные теги (Settings - Repository - Protected tags, создавать - Maintainers):
  пайплайн от незащищенного тега не создается;
- перезапуск кластера после загрузки `.cf` - только кнопкой: задание ручное и блокирующее, до нажатия пайплайн
  стоит, Обновление ждет.

Как пайплайн получает историю: задание берет рабочую копию с глубиной 1, а генератору нужна вся история и теги.
Поэтому на раннере голое зеркало репозитория (`sync_repo.ps1`, `EF_MIRROR`): первый раз оно клонируется целиком,
дальше только `fetch` токеном задания.

Что нужно настроить:

1. Раннер проекта (shell, PowerShell) с тегом из `EF_RUNNER_TAG`.
2. Защитить основную ветку.
3. На сервере: `setup_server.ps1` (каталоги и служба автономного сервера сборки), Python (подойдет архив
   embeddable, путь в `EF_PYTHON`), EDT (путь в `EF_EDT_CLI`), автономный сервер для сборки (каталог данных
   в `EF_SERVER_DATA`).
4. Для этапа Установка: в рабочей базе расширение RepEr с HTTP-сервисом `reperext`, сервис опубликован
   на веб-сервере, пользователь базы с ролью `ПроверкаИсправлений_RepEr`; переменные проекта `EF_IB_URL`,
   `EF_IB_USER`, `EF_IB_PASSWORD` (masked), см. "Проверка установки". Пока `EF_IB_URL` пуст, этап ничего не проверяет.
5. Для задания Загрузка: Конфигуратор (`1cv8.exe`) в `EF_PLATFORM` на раннере и лицензия для него, переменная
   проекта `EF_PROD_IB` (`<сервер>\<база>`), у пользователя `EF_IB_USER` - право администрирования,
   см. "Загрузка .cf в рабочую базу".
6. Для перезапуска и обновления: `EF_LOCK_CODE`, при необходимости `EF_CLUSTER_USER` и `EF_CLUSTER_PASSWORD`.
7. Защищенные теги релиза, см. выше.

## Сборка .cfe

`build_cfe.ps1` передает работающему автономному серверу (ibsrv) одну операцию:
`ibcmd infobase config import --pid=<процесс> --extension=<имя> --out=<имя>.cfe <каталог xml>`.
Расширение записывается сразу в файл и в базе сервера не остается.

| Способ | Время на расширение |
|---|---|
| через работающий сервер (`-ServerData`, `-ServerPid` или `-Remote`) | 0.2-0.4 с на операцию ibcmd, около 1 с весь скрипт |
| временная файловая база (сервер не задан) | около 4 с: создание базы и импорт |

Серверу подходит любая база, в том числе пустая: ibcmd при импорте расширения не сверяет его
с конфигурацией. Требования:

- база без пользователей либо учетные данные в `EF_SERVER_USER` и `EF_SERVER_PASSWORD` (с ними не проверялось).
  Не `EF_IB_USER`: это пользователь рабочей базы для этапа Установка, с ним ibcmd на пустой базе завершается с кодом -1.
  Без них ibcmd запрашивает имя с клавиатуры, скрипт в этом случае завершится по времени ожидания;
- процесс сервера ищется по каталогу данных в командной строке ibsrv. Файл `lock.pid` сервер держит
  открытым монопольно, прочитать его нельзя. Если сервер запущен службой под другой учетной записью
  и командная строка не видна, задать `-ServerPid` или `-Remote`;
- на узле кластера у сервера выключен шлюз прямого подключения (`features: direct-gate: "no"`
  в `config.yaml`): иначе ibsrv занимает порт 1541 агента кластера и не стартует.

`setup_server.ps1` ставит сервер службой `release-ibsrv` (LocalSystem, автозапуск), каталог данных
`D:\cicd\ibsrv`, слушает только `127.0.0.1:18430`. Сборка через нее -
около 2 с на исправление вместе с запуском PowerShell.

Замеры на полной конфигурации (файловая база, 8.3.27.2325), пригодятся для сборки релиза по тегу:
`ibcmd infobase create --load=<cf около 1 ГБ>` - 25 с, `ibcmd infobase config apply` - 69 с.

## Сборка .cf релиза

Тег релиза в репозитории конфигурации запускает задание Релиз (`release_cf.py`). Оно кладет в `<EF_CF_DIR>\<тег>\`
на раннере файл `<applied_name>_<тег>.cf` и `release.md`: коммит тега, версия из модуля `version_module`,
размер и SHA-256 файла, задачи и коммиты после предыдущего тега. В рабочую базу файл загружает следующее задание,
Загрузка, сразу после сборки (см. "Загрузка .cf в рабочую базу").

Как собирается:

1. Рабочая область EDT с проектом конфигурации (`edt_base_project`) из тега - та же, что у проверки исправлений (`EF_EDT_WORKSPACE`).
   На новом теге она обновляется разницей между тегами (см. "Проверка"), и первая проверка исправлений
   после тега ее уже не ждет.
   Задания Релиз и Проверка выполняются по очереди (`resource_group: edt-release`).
2. `1cedtcli export` выгружает проект в XML.
3. `ibcmd infobase config import --out=<файл>.cf` во временной файловой базе собирает из XML файл конфигурации.
   Через автономный сервер не быстрее: он экономит только создание базы, а оно занимает секунду.
4. Файл копируется в каталог релиза через временное имя; XML и временная база удаляются.

Повторная сборка тега перезаписывает его файлы. Тег, не подходящий под `base_tag_match`, и удаление тега
пропускаются. В `EF_CF_DIR` хранятся последние 5 релизов по номеру тега (`EF_CF_KEEP`, 0 - не удалять): после сборки более старые удаляются. Только что собранный тег не удаляется, даже если он старше пяти последних
(ручная пересборка). Релизом считается каталог с `release.md`, остальное в `EF_CF_DIR` не трогается.

Запуск:

- тег в репозитории конфигурации; тег, не подходящий под `base_tag_match`, задание пропускает;
- вручную: Run pipeline с переменной `EF_RELEASE_TAG` (например `3.20`) - для пересборки и первого релиза.

## Загрузка .cf в рабочую базу

Задание Загрузка запускается сразу после задания Релиз. `load_cf.ps1` объединяет `.cf` релиза с основной
конфигурацией рабочей базы - Конфигуратор в пакетном режиме:

```
1cv8.exe DESIGNER /S <EF_PROD_IB> /N <EF_IB_USER> /P <EF_IB_PASSWORD> /DisableStartupDialogs /Out build/release/load.log
  /MergeCfg <EF_CF_DIR\<тег>\<applied_name>_<тег>.cf> -Settings merge-all.xml -force
```

Конфигурация базы данных не обновляется (`/UpdateDBCfg` нет): изменения проверяются в Конфигураторе и применяются
вручную. Отказаться от загруженного - "Конфигурация - Конфигурация базы данных - Вернуться к конфигурации БД".
Путь к `.cf` задание берет из dotenv-артефакта задания Релиз (`build/release/release.env`: `RELEASE_TAG`, `RELEASE_CF`);
если релиз не собирался, загружать нечего. Журнал Конфигуратора - артефакт `build/release/load.log`.
Загрузить уже собранный `.cf` без сборки - Run pipeline с переменной `EF_RELEASE_CF`
(например `D:/CF/3.20/system_3.20.cf`): пайплайн состоит из одного задания Загрузка, оно запускается сразу.

`merge-all.xml` - файл настроек объединения (схема `http://v8.1c.ru/8.3/config/merge/settings`, лежит в ресурсе
платформы `bin\frntend_root.res`): вторая конфигурация - потомок основной (`SecondConfigurationIsDescendantOfMainConfiguration`),
корень конфигурации и порядок объектов - из файла, удаление объектов основной конфигурации разрешено. Правила
на корне достаточно, объекты перечислять не нужно. В отличие от загрузки `.cf` целиком, объединение не трогает объекты
без расхождений.

Проверено локально на временных файловых базах (8.3.27.2325): база на старом теге, `/MergeCfg` с `.cf` нового,
итог выгружен в XML и сравнен с XML нового тега.

| Переход | Объединение и обновление БД | Итог |
|---|---|---|
| релиз - master | около 2 минут | совпал с master полностью |
| предыдущий релиз - следующий | около 2 минут | удаленный в релизе регистр удален; отличия - явная запись стандартных реквизитов новых объектов со значениями по умолчанию и права на корень конфигурации у двух ролей (см. ниже) |

Роль без записи прав на корень конфигурации (`Configuration.<имя>` в `Rights.rights`) после загрузки из XML
не имеет этих прав, а Конфигуратор при объединении измененной такой роли выдает ей права по умолчанию: режимы
основного окна и клиент системы аналитики. Поэтому права на корень записываются в каждой роли явно, даже если все сняты.

Требования: на раннере Конфигуратор той же версии, что кластер (`EF_PLATFORM`), и лицензия для него;
у пользователя `EF_IB_USER` право администрирования (см. "Проверка установки"); основная конфигурация не захвачена другим
Конфигуратором. Пароль передается Конфигуратору в командной строке, в журнал задания она не выводится.

## Перезапуск кластера

Задание Перезапуск (`cluster_restart.ps1`) - кнопкой после Загрузки или отдельным пайплайном с переменной
`EF_CLUSTER_RESTART`: `check` - только проверка, ничего не меняет; `run` - перезапуск сразу, за ним Обновление;
`restart` - только перезапуск, без Обновления: после шага 6 блокировка снимается (`-ThenUnlock`). Шаги:

1. Блокировка начала сеансов и регламентных заданий базы из `EF_PROD_IB` с текущего момента: `rac infobase update`
   через RAS (`EF_RAS`, по умолчанию `localhost:1545`), сообщение `EF_LOCK_MESSAGE`, код разрешения `EF_LOCK_CODE`,
   пользователь базы `EF_IB_USER`; администратор кластера, если задан, - `EF_CLUSTER_USER`, `EF_CLUSTER_PASSWORD`.
2. Остановка служб агента на узлах `.reper/cluster.json` в их порядке. Перед агентом останавливаются другие
   службы 1С узла (`extraServices`), например `release-ibsrv` - автономный сервер сборки исправлений. Он тоже
   держит файлы платформы; остановленный вручную и не запущенный, он ломает Сборку: "Автономный сервер с каталогом
   данных ... не запущен".
3. Ожидание завершения `ragent`, `rmngr`, `rphost` на всех узлах; через `EF_STOP_TIMEOUT` (600 с) оставшиеся
   завершаются принудительно.
4. Удаление `<srvinfo>/reg_*/snccntx*`.
5. Запуск служб в том же порядке, другие службы 1С - после агента. Если другая служба не запустилась, задание
   не падает (от него зависит Обновление), а в конце журнала пишет "ВНИМАНИЕ: не запустилась, запустить вручную".
6. Полное применение требований назначения функциональности (`rac rule apply --full`, как "Применить требования
   назначения функциональности (полное)" в консоли): без него после перезапуска сервер может не выдавать лицензии
   ("На сервере 1С:Предприятия не найдена лицензия"). Кластер после запуска служб
   отвечает не сразу - повтор до 3 минут.

Блокировка остается: конфигурация базы данных обновляется с кодом разрешения, затем блокировка снимается.
Перед перезапуском скрипт выполняет ту же проверку, что `check`, и при любой проблеме ничего не меняет: база в RAS,
службы, доступ по SSH и sudo, каталоги. Если процессы не завершились или каталоги не удалились, задание падает
с остановленными службами и включенной блокировкой.

Узел раннера (Windows) обслуживается локально. Linux-узлы - по SSH под учеткой `sshUser` с ключом `sshKey`
(профиль LocalSystem), ключи узлов - в `.reper/known_hosts`; команды - через `sudo -n`. Учетке на Linux-узлах
нужен sudo без пароля для `systemctl stop|start <служба>`, `pkill -9 -x ragent|rmngr|rphost`
и `find /srv/srvinfo ... -exec rm -rf`. Имена служб и каталоги данных - в `cluster.json`, `check` показывает
службы 1С на узле, если имя не совпало.

Кластер останавливается целиком: все базы на этих серверах недоступны до запуска служб.

## Обновление рабочей базы и снятие блокировки

Задание Обновление (`update_db.ps1`) запускается само после Перезапуска или отдельным пайплайном с `EF_DB_UPDATE=run`.
Под блокировкой, с кодом разрешения `EF_LOCK_CODE` (`/UC`), пользователь `EF_IB_USER`:

0. Полное применение требований назначения функциональности (`rac rule apply --full`), еще раз после Перезапуска:
   применения сразу после запуска служб оказалось мало - сервер не выдавал лицензии, пока ТНФ не применили повторно.
1. Конфигуратор `/UpdateDBCfg -Dynamic-` - конфигурация базы данных по основной (загруженной заданием Загрузка).
   Затем удаляются исправления без манифеста: Конфигуратор выгружает все расширения (`/DumpConfigToFiles -AllExtensions`),
   исправлением считается расширение с назначением "Исправление" и именем на `EF` (как `ОбновлениеКонфигурации.ЭтоИсправление`),
   манифестом - общий макет с именем расширения. Исправления без манифеста (собранные вручную) БСП не удаляет никогда,
   считая их еще не примененными, поэтому их удаляет `/DeleteCfg -Extension`. Исправления с манифестом - из ленты
   и официальные исправления 1С - удаляет или оставляет БСП по применимости к версии.
2. Предприятие `/C"ЗапуститьОбновлениеИнформационнойБазы;ЗавершитьРаботуСистемы"` - обновление версии, как в скрипте
   обновления БСП: обработчики обновления, исправления, не применимые к новой версии, удаляются.
3. Ожидание фоновых заданий пользователя `EF_IB_USER` (`rac session list`, `app-id` `BackgroundJob`): обновление идет
   фоновым заданием в монопольном режиме, и клиент Предприятия завершается раньше него (клиент может закончить
   за минуту, а фоновое задание держит базу и после). Если за минуту такой сеанс не появился, обновление
   уже закончилось.

Каждый запуск ограничен `EF_UPDATE_TIMEOUT` (3600 с). Журналы - артефакты `build/release/update_db.log`
и `build/release/enterprise.log`. Регламентные задания заблокированы, поэтому отложенные обработчики обновления
пойдут после снятия блокировки.

Задание Снятие блокировки (`cluster_restart.ps1 -Unlock`) - только кнопкой, после проверки базы, или отдельным
пайплайном с `EF_UNLOCK=run`: `rac infobase update --sessions-deny=off --scheduled-jobs-deny=off`, службы не трогает.

## Лента исправлений

Каталог на версию релиза (`1.3.20.01/`): архивы `EF_<задача>_<n>_<версия>.zip` и оглавление `index.json`.
В оглавлении на каждую сборку: UUID, имя, порядок установки (`order`), описание, измененные объекты,
перехватываемые и добавленные методы (`methods`), файл, размер, sha256, коммиты, признак `revoked`. При пересборке
исправления прежняя сборка помечается `revoked` - по этому признаку база удалит ее перед установкой новой.
Когда исправления больше нет (коммиты откачены или вошли в другое исправление), публикация отзыва помечает
`revoked` все его сборки, и база удаляет его совсем.

## Проверка установки

Этап Установка (`ef_verify.py`) ждет, пока база поставит исправления, опубликованные пайплайном, и проверяет, что они
подключаются. Ставит их сама база: регламентное задание загрузки (`ВключитьЗагрузку`) или вручную обработка
«Исправления из репозитория». Пайплайн только спрашивает базу через HTTP-сервис расширения RepEr:
`GET <публикация>/hs/reperext/patches?since=<дата>`. Ответ - исправления в базе (имя, идентификатор описания, версия,
подключение: `attached`, `pending`, `failed`, `disabled`, сеансы, начатые до подключения) и ошибки загрузки
(событие журнала регистрации «Репозиторий исправлений» с даты `since`, без повторов). Сеансы сервиса
не переиспользуются, поэтому подключение в сеансе сервиса такое же, как в любом новом сеансе.

Что считается установленным:

- собранное исправление - в базе сборка с UUID из `ef.json` (у неподключенного расширения база не видит описание,
  тогда сборку выдает версия) и она подключается. Более новая сборка того же исправления тоже подходит:
  ее мог опубликовать следующий пайплайн;
- отзыв - исправления в базе нет.

База опрашивается раз в минуту не дольше `EF_VERIFY_TIMEOUT` (15 минут). «Не удалось подключить» и снятый флажок
«Подключать» - ошибка сразу, HTTP 401, 403 и 404 (нет роли, неверный пароль, в базе расширение RepEr без сервиса) - тоже.
Не дождались - задание падает с тем, что не установлено, и ошибками загрузки, итог в `build/ef/verify.md`.
Пока исправления ставятся вручную, так и задумано: красное задание напоминает об установке, а после нее задание
достаточно перезапустить (Retry), проверка пройдет сразу. У срочного исправления в отчете - число сеансов,
начатых до подключения: в них еще работает прежняя версия.

Итог синхронизации (установлены, удалены, ошибки) расширение пишет в журнал регистрации и при ручном запуске,
не только в регламентном задании: этап Установка показывает эти ошибки.

Технический пользователь - отдельный. Этапу Установка достаточно роли `ПроверкаИсправлений_RepEr` (право «Использование» на метод
`Получить` HTTP-сервиса и больше ничего; права на HTTP-сервис в 1С задаются по методам, право на сам сервис платформа
не применяет, и без права на метод сервис отвечает 403): состояние сервис читает в привилегированном режиме и в базе ничего не меняет, а проверка прав на вход
в БСП выполняется только при запуске клиента, не в HTTP-сеансе. Роли пользователям конфигураций на БСП назначает управление
доступом по профилям групп доступа (роль, выданная напрямую, сбросится), поэтому:

1. Профиль групп доступа «Проверка исправлений из репозитория» - одна роль `ПроверкаИсправлений_RepEr`.
2. Группа доступа с этим профилем.
3. Пользователь - формой или кодом под администратором (консоль кода), если форма пользователя конфигурации
   ставит свои требования к имени. Описание пользователя ИБ - `Пользователи.НовоеОписаниеПользователяИБ(Истина, Истина)`
   (служебный: без ОС, скрыт из списка выбора, пароль менять и восстанавливать нельзя), плюс имя, стандартная
   аутентификация с паролем, `ВходВПрограммуРазрешен` и `Действие = "Записать"` в `ДополнительныеСвойства.ОписаниеПользователяИБ`
   элемента справочника `Пользователи`; затем группа доступа из п. 2 с этим пользователем. Роли пользователю ИБ
   выставит управление доступом (ровно `ПроверкаИсправлений_RepEr`).
4. Имя и пароль - в переменные `EF_IB_USER`, `EF_IB_PASSWORD` (masked, protected) проекта.
5. Для задания Загрузка (Конфигуратор) тому же пользователю нужно право администрирования: еще одна группа доступа
   с профилем «Администратор». Тогда пользователь уже не только читает состояние исправлений - пароль хранить
   соответственно.

Сервис нужно опубликовать на веб-сервере: в `default.vrd` публикации строка
`<service name="СостояниеИсправлений_RepEr" rootUrl="reperext" enable="true" reuseSessions="dontuse"/>` в `<httpServices>`
(или публикация сервисов расширений по умолчанию). Сеансы не переиспользовать: иначе сеанс, начатый до установки
исправления, покажет прежнее подключение.

Технологический журнал для этой проверки не подходит: отдельного события установки расширения в нем нет,
а установку делает фоновое задание на любом рабочем сервере кластера,
поэтому логи пришлось бы собирать со всех узлов. Факт установки (имя, UUID, хеш, флажок «Подключать») платформа
пишет в журнал регистрации: `_$InfoBase$_.DBConfigExtensionInsert`, `...Update`, `...Delete`.

## Проверка

Проверять расширение нужно относительно релиза, а не текущего master. Пример: исправление
добавляет метод, который позже вошел в master; рядом с проектом, где этот метод уже есть, EDT выдает блокирующую
ошибку "Повторяющееся имя метода", а платформенный `ПроверитьВозможностьПрименения` ошибок не находит.

Автономный сервер проверку не заменяет. На базе с полной примененной конфигурацией `ibcmd config import`,
`config check` и `config apply` прошли без ошибок для заведомо сломанного расширения: заимствован
несуществующий общий модуль, `&Вместо` для несуществующего метода, дубль существующего метода.
Модули ibcmd не компилирует, такие ошибки проявятся только в сеансе.

Проверку делает `ef_check.py`:

1. **Рабочая область релиза.** Отдельная рабочая область EDT, в ней проект конфигурации из тега релиза.
   В каталоге области лежит отметка `ef-release.json` с коммитом тега, исходники проекта - в `<область>-src`.
   - Первый раз (или без отметки) область готовится с нуля: исходники выгружаются `git archive`, проект
     импортируется и собирается - на полной типовой конфигурации около получаса.
   - На другом теге в исходники накладывается разница между тегами (`git diff`: новые и измененные файлы
     пишутся, удаленные удаляются вместе с опустевшими каталогами), затем `build`. Импорт не нужен: EDT при
     запуске сам замечает измененные файлы. Между соседними релизами это обычно десятки файлов вместо десятков тысяч.
     Проверено на небольшом проекте (312 модулей, удаленные и добавленные объекты): замечания и выгрузка
     в XML совпали с областью, подготовленной с нуля.
   - С нуля область готовится и тогда, когда обновить не вышло (сборка завершилась с ошибкой, разница
     недоступна), изменений больше 5000 файлов (обновление типовой) или задана переменная `EF_EDT_FULL=1` -
     на случай, если EDT накопит расхождения.
   - Отметка на время обновления удаляется: прерванное обновление в следующий раз приведет к подготовке с нуля.
2. **Проверка.** Для каждого `build/ef/EF_*/<проект>.EF_*` - `validate` (сам импортирует проект расширения
   в область) и `delete`. Все команды идут одним запуском `1cedtcli -file`, чтобы не платить
   за старт EDT на каждое исправление.
3. **Итог.** Ошибкой считаются замечания с важностью "Ошибка конфигурации" и "Блокирующая" -
   например, "Функция не определена" или "Повторяющееся имя метода". Замечания стандартов кодирования
   в отчет попадают, но сборку не останавливают: сгенерированный код получает их всегда (префикс
   имени макета, методы вне областей, рекомендация `&ИзменениеИКонтроль`). Результат - `check.md`
   и `check.tsv` рядом с исправлением и поле `check` в `ef.json`. Есть ошибки - код возврата 1,
   публикация в CI не запустится.

Проверено на локальном EDT 2026.2 и учебном репозитории: исправление, которое вызывает функцию,
добавленную после релиза без пометки EF, отклоняется с ошибкой "Функция 'НеВРелизе' не определена".
Подготовка области с мини-конфигурацией и проверка двух исправлений - 52 с, повторная проверка - 24 с.
На полной типовой конфигурации (EDT 2026.2, `-Xmx16g -XX:ActiveProcessorCount=4`): подготовка области - около
получаса, проверка двух исправлений на готовой области - около минуты.

Отчет EDT пишется на языке, заданном `-nl` (по умолчанию `ru_RU`, переменная `EF_EDT_NL`):
без этого на сервере с английской ОС сообщения были бы по-английски.

В исходниках типовых конфигураций есть файлы вложенных подсистем с путем длиннее 260 символов (самый длинный - 353),
поэтому исходники релиза распаковываются через пути с префиксом `\\?\`.

Каталог проекта EDT назван по имени проекта (`<проект>.EF_<номер>`): при импорте EDT берет имя проекта
из имени каталога, и два каталога `edt` конфликтуют.

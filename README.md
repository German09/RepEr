# RepEr - Reporter Error

Сервер регистрации ошибок для конфигураций 1С:Предприятие 8.3. Принимает отчёты об ошибках, которые платформа отправляет через штатный механизм «Центр обработки ошибок» (сервис регистрации ошибок, 8.3.17+), сохраняет их в базе, группирует повторы, показывает пользователю понятное сообщение и автоматически заводит задачи в Jira, GitHub или GitLab с прикреплением скриншотов, стека и коммитов по затронутым модулям.

- Конфигурация: `RepEr`, версия 3.5.0.0, режим совместимости 8.3.24
- Построена на Библиотеке стандартных подсистем (БСП)
- Собственные объекты помечены суффиксом `_RepEr` (ядро) и `_RepEx` (внешние подключения)
- Формат исходников: 1C:EDT (`src/`)

## Состав репозитория

| Часть | Где | Что это |
|---|---|---|
| Конфигурация RepEr | `src/` (проект EDT в корне) | сервер регистрации ошибок, см. ниже |
| Расширение RepEr | `extension/` | ставится в базы, которые отправляют ошибки в RepEr: загрузка и установка исправлений (EF) из ленты, состояние исправлений для пайплайна. См. [extension/README.md](extension/README.md) |
| Пайплайн | `pipeline/`, `template/`, `install.ps1` | исправления EF из коммитов репозитория конфигурации: сборка, проверка в EDT относительно релиза, публикация в ленту; `.cf` релиза по тегу, загрузка в рабочую базу, перезапуск кластера, обновление базы. См. [pipeline/README.md](pipeline/README.md) |

Пайплайн ставится в репозиторий конфигурации копией: `powershell -File install.ps1 -Target <репозиторий>`
кладет скрипты в `.reper/pipeline`, задания - в `.reper/reper.gitlab-ci.yml`, а при первой установке - `.gitlab-ci.yml`
и примеры настроек `.reper/config.json`, `.reper/cluster.json`. Серверы, пароли и адреса проекта хранятся только
в репозитории проекта и его переменных CI, в RepEr их нет.

Ошибки в исправлениях `EF_<номер>_...` RepEr заводит подзадачами к задаче `<номер>` - так три части связаны
кодом задачи из коммита.

## Как это работает

```
Прикладная база 1С                      RepEr
────────────────────                    ──────────────────────────────────────────
ошибка у пользователя
  │  GET /reper/hs/reper/{InfoBaseCode}/getInfo
  ├───────────────────────────────────►  РС Ошибки_RepEr  (факт ошибки + хеши стека)
  │  ◄─── needSendReport / userMessage   подсчёт повторов, текст пользователю
  │
  │  POST /reper/hs/reper/{InfoBaseCode}/pushReport
  └───────────────────────────────────►  РС Отчеты_RepEr  (сырой отчёт, ХранилищеЗначения)
                                                │
                                   регл. задание «Распаковка отчетов»
                                                ▼
                                   Документ ОтчетыОбОшибках_RepEr
                                   (стек, ошибки, скриншоты, файлы, основание)
                                                │  проведение
                                                ▼
                                   Оповещения_RepEr → Jira / GitHub / GitLab
                                   Репозитории_RepEr → коммиты по модулям (GitLab)
```

1. **Регистрация факта ошибки** (`getInfo`). Платформа сообщает хеши конфигурации и стеков (`configHash`, `appStackHash`, `clientStackHash`, `serverStackHash`). RepEr пишет запись в регистр `Ошибки_RepEr` и отвечает:
   - `needSendReport` - клиенту предлагается отправить отчёт всегда, для серверных ошибок - пока не накопится 6 отчётов по одному стеку;
   - `userMessage` - текст для пользователя: номер уже зарегистрированной задачи, сколько раз ошибка повторялась, сколько отчётов получено, или просьба отправить отчёт;
   - `dumpType` - тип дампа.
2. **Приём отчёта** (`pushReport`). Тело запроса сохраняется как есть в регистр `Отчеты_RepEr`.
3. **Распаковка**. Регламентное задание `РаспаковкаОтчетов_Reper` разбирает накопленные отчёты в документы `ОтчетыОбОшибках_RepEr`: текст ошибки, время, пользователь, стек вызова (расширение, модуль, строка), скриншоты и файлы. Повторы одной ошибки привязываются к первому документу через реквизит `Основание`.
4. **Оповещение**. При проведении документа для каждой активной настройки оповещения информационной базы вызывается обработчик провайдера:
   - новая ошибка - создаётся задача (issue) с описанием, стеком, расшифровкой ошибок и коммитами по затронутым модулям, прикладываются скриншоты;
   - повтор ошибки - к задаче добавляется комментарий;
   - если ошибка произошла в исправительном расширении с именем вида `EF_<номер>_...`, в Jira создаётся подзадача к родительской задаче `<номер>` и ставится связь.
   
   Идентификатор созданной задачи хранится в регистре `КлючиОповещений_RepEx`. Тексты ошибок из списка **Исключения** информационной базы (стоп-слова) не оповещаются.
5. **Журнал регистрации**. Если в дополнительной информации отчета есть адрес базы (ключ `ib`, см. настройку ниже), в задаче и в комментарии под строкой «Пользователь» появляется ссылка «Журнал регистрации пользователя +/- 10 минут» вида `<адрес публикации базы>#e1cib/command/ОбщаяКоманда.ЖурналРегистрацииПоОшибке_RepEr?cmdprm=...`. Ссылка открывает базу в веб-клиенте и журнал регистрации с отбором по пользователю отчета и периоду от времени ошибки -10 до +10 минут. Отбор передает команда расширения RepEr `ЖурналРегистрацииПоОшибке_RepEr`: платформа передает в команду по ссылке (`?cmdprm=`) только ссылки, поэтому период и имя пользователя записаны в UTF-8 шестнадцатеричными цифрами в уникальные идентификаторы несуществующих элементов `Справочник.Пользователи`.

## Состав

| Объект | Назначение |
|---|---|
| `HTTPService.RepEr` (`/reper`) | Точки входа `getInfo`, `pushReport`, `version` |
| `Catalog.ИнформационныеБазы_RepEr` | Обслуживаемые базы: код = `{InfoBaseCode}` в URL; ТЧ **Оповещения**, **Репозитории**, **Исключения** |
| `Catalog.НастройкиПодключений_RepEx` | Подключение к внешнему сервису: провайдер, ссылка на проект, токен (у Jira - и пользователь для авторизации по паролю), путь к исходникам у репозиториев. Адрес сервиса и проект заполняются по ссылке при записи; кнопка «Проверить подключение» |
| `HTTPService.Service` (`/service`) | Для баз с расширением RepEr: лента исправлений из GitLab (`patches`), пользователи с ошибками по задачам (`issue`, `issues`) |
| `Role.ПолучениеИсправлений_RepEr` | Пользователю RepEr, под которым базы обращаются к `HTTPService.Service` |
| `Enum.Провайдер_RepEx` | Jira, GitHub, GitLab |
| `Document.ОтчетыОбОшибках_RepEr` | Распакованный отчёт об ошибке; команды **Заполнить**, **Исправить** |
| `InformationRegister.Ошибки_RepEr` | Факты ошибок с хешами и ответом сервиса |
| `InformationRegister.Отчеты_RepEr` | Очередь сырых отчётов до распаковки |
| `InformationRegister.КлючиОповещений_RepEx` | Соответствие документ ↔ задача во внешней системе |
| `ScheduledJob.РаспаковкаОтчетов_Reper` | Периодическая распаковка отчётов |
| `Role.ПросмотрИРегистрация_RepEr` | Минимальная роль для пользователя, от имени которого публикуется HTTP-сервис |
| `CommonModule.Оповещения_RepEr`, `ОповещенияJira_RepEx`, `ОповещенияGitHub_RepEx` | Диспетчер и обработчики провайдеров задач |
| `CommonModule.Репозитории_RepEr`, `РепозиторииGitLab_RepEr` | Поиск коммитов по модулям из стека (blame) |
| `CommonModule.КоннекторHTTP_RepEr*` | HTTP-клиент для обращений к внешним API |

## Установка и настройка

1. Загрузить конфигурацию из `src/` (1C:EDT) в информационную базу, выполнить обновление.
2. Опубликовать базу на веб-сервере с HTTP-сервисом `RepEr`, **только с анонимным доступом**. Создать пользователя с ролью «Просмотр и регистрация ошибок» и указать его в публикации.
3. В справочнике **Информационные базы** завести элемент на каждую обслуживаемую базу (предопределённый элемент с кодом `InfoBase` уже есть). Заполнить:
   - **Оповещения** - куда заводить задачи (настройка подключения к Jira/GitHub/GitLab);
   - **Репозитории** - откуда брать коммиты по модулям;
   - **Исключения** - фрагменты текста ошибок, о которых оповещать не нужно.
4. В обслуживаемой базе в разделе *Администрирование → Настройки отображения ошибок* (для клиента и сервера) указать адрес сервиса:
   ```
   http://<сервер>/<публикация>/hs/reper/<InfoBaseCode>/
   ```
5. Включить регламентное задание «Распаковка отчетов» и убедиться, что работа с внешними ресурсами не заблокирована (БСП).
6. Чтобы из задачи открывать журнал регистрации (необязательно):
   - в обслуживаемую базу поставить расширение RepEr (`extension/`);
   - в обслуживаемой базе в *Все функции → Стандартные → Управление настройками обработки ошибок* добавить в поле «Дополнительная информация» ключ `ib` с адресом публикации базы на веб-сервере, остальные ключи не трогать (`guid` пишет Центр мониторинга БСП и сохраняет чужие ключи):
     ```
     {"guid":"...","version":"...","ib":"https://<сервер>/<публикация>"}
     ```
     Без ключа `ib` ссылка в задаче не появляется. Ключ действует для отчетов, полученных после его установки.

## Лента исправлений и пользователи ошибок для баз

Расширение RepEr в обслуживаемой базе читает ленту исправлений не из GitLab, а через HTTP-сервис `Service` той RepEr,
в которую база отправляет ошибки: адрес берется из настроек обработки ошибок базы, `.../hs/reper/<InfoBaseCode>/`
заменяется на `.../hs/service/<InfoBaseCode>/`. Токен GitLab есть только в RepEr - в настройке подключения
к проекту, deploy-токен в базах не нужен.

| Запрос | Ответ |
|---|---|
| `GET /hs/service/{InfoBaseCode}/patches/{Version}/{FileName}` | файл ленты: `index.json` или архив исправления из generic-пакета `ef` первого используемого репозитория GitLab информационной базы. Для версии без публикаций - пустое оглавление `{"patches": [], "not_found": true}`; 404 - нет базы, репозитория GitLab или архива; 502 - GitLab не ответил или не принял токен |
| `GET /hs/service/{InfoBaseCode}/patches/{Version}` | `{"page": "<страница версии пакета в GitLab>"}` |
| `GET /hs/service/{InfoBaseCode}/issue/{IssueKey}/users` | имена пользователей, сообщивших об ошибках по задаче |
| `POST /hs/service/{InfoBaseCode}/issues/users/count` | число таких пользователей по списку задач |

Настройка:

1. В справочнике **Информационные базы** код базы - тот, что в адресе сервиса обработки ошибок (`InfoBase` у предопределенной).
   Если код совпадает с именем библиотеки в описаниях подсистем базы (код `SYSTEM` - библиотека `system`), расширение берет эту библиотеку,
   иначе - выбранную в его настройках. Код может быть на русском.
2. У базы в **Репозиториях** - настройка подключения к GitLab-проекту с лентой (пакет `ef`), токен со scope `read_api`.
3. Пользователь RepEr с ролью «Получение исправлений и пользователей ошибок» - его логин и пароль указываются
   в настройках репозитория в расширении. Заголовок авторизации расширение передает сразу, не дожидаясь ответа 401.
4. Публикация RepEr - с HTTP-сервисом `Service` (`rootUrl="service"`) рядом с `RepEr`.

Данные сервис читает в привилегированном режиме: кроме роли пользователю ничего не нужно.

## Разработка

- Проект 1C:EDT, корень репозитория; исходники в `src/`. Расширение - отдельный проект EDT в `extension/`.
- Тесты пайплайна: `python -m unittest discover -s pipeline/tests`.
- Основная ветка - `master`.
- Типовые модули БСП не изменяются напрямую: доработки размещаются в модулях с суффиксом `_RepEr` / `_RepEx`.
